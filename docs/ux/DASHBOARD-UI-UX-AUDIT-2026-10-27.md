# Dashboard UI/UX audit — 27 October 2026

## Result and exact scope

All **81 `page.tsx` routes beneath `src/app/(dashboard)`** have an individual review below, including dynamic detail/edit/fill routes and the developer-only diagnostics route. The earlier figure of 85 counted the dashboard layout, loading and error files as well as pages. Public pages, authentication, subscription/onboarding and the mobile application are excluded.

The principal problem is inconsistent task boundaries and action scope, compounded by unreliable recovery states. The application already has useful tables, focused setup dialogs, responsive navigation, permission gates and a workable design system. Rebuilding those foundations or applying the event tab pattern everywhere would be counterproductive.

This pass changes **audit documentation and evidence only**. It does not implement the recommendations, alter business rules, change backend contracts or deploy the application. The event-workflow changes from the preceding implementation remain part of the reviewed baseline.

## Method and limits

**Source review:** inspected each page's UI structure, controls, local state, data-hook usage and error/loading handling. Followed thin route wrappers into the real dashboard, department detail, people importer, form builder, sermon editor, user account, settings/integration and support components. Checked shared table/header/form/dialog patterns, navigation, route permissions and plan gates. Source anchors below identify the specific evidence for a finding; they are not a substitute for reading the surrounding workflow.

**Browser recovery sweep:** visited all 81 route patterns with deterministic identifiers and a valid synthetic HQ staff session/profile with all catalogued grants and plan features. Domain-data GETs returned controlled 503 responses; session restoration, profile and basic notification responses were valid fixtures. Each route was examined at 1440, 768 and 390px: **243 viewport observations**. The production-only `/debug/sentry` 404 was expected. External chat/provider requests were blocked; their induced availability notices are excluded from product findings and dismissed in the retained overflow screenshots. Error-state snapshots are evidence about recovery and layout, not about real record availability. A selector that has not selected a record cannot demonstrate the later record-list failure path; those paths are identified from source and need interaction regression coverage when changed.

**Selected populated views:** supplemented the sweep with 14 route examples using repository browser fixtures, adding explicit plan entitlements in the temporary audit harness where older fixtures omitted them. These cover form details/edit/fill/submissions, template and broadcast lists/composition, the event calendar, a sermon, assets/loans/maintenance, service detail and user detail. They are synthetic examples, sometimes with empty related panels or restricted actions. They do not establish that every page, every dialog, every record size or every role was visually tested in a populated state.

**Verification:** the existing `audit-ui-contracts.mjs --inventory` check reported no issues for its static link/navigation/route-gate checks. That is useful evidence of wiring consistency, not certification of live authorisation, business mutations, keyboard accessibility or information architecture. No live church records, credentials or provider accounts were used; no live writes or messages were sent. No intentional diagnostic trigger was clicked. This documentation-only pass did not rerun application builds/unit tests and does not reuse the preceding turn's test totals as new audit coverage.

Browser failure results contained no captured page runtime exceptions in the final supported service-worker/session harness. The scope is a UX/code audit with controlled Chromium inspections, not a full assistive-technology, cross-browser, performance, security or live-data acceptance audit.

## Architecture and design system to preserve

- Installed Next.js 15.5.27 and React 19.2.8; App Router. The dashboard layout wraps the existing workspace frame. No new client boundary is needed for these recommendations by default.
- Tailwind 4 and existing theme tokens, shadcn-style Radix components, Lucide/Tabler icons, React Query, React Hook Form and Zod. Keep this system; do not introduce another UI library.
- Fetch/mutation hooks use the same-origin backend proxy and cache invalidation. Permissions and subscription features are independent, fail-closed UI gates; the API remains authoritative. Preserve branch/HQ and own-group constraints.
- Shared Table handles scrolling, pinned identifiers, visibility, density, selected-row export and keyboard focus for its scroll region. Preserve those functions while reducing the always-visible configuration controls.
- The shared Form **already includes a draft guard** for dirty React Hook Form fields on anchor navigation and browser unload. Do not report all forms as unprotected. Gaps involve programmatic route buttons, same-page tabs/unmounting, state outside React Hook Form and reset-on-refetch paths.
- Event registrations versus check-in, aggregate attendance versus named attendees, and group giving versus personal giving are distinct concepts. A redesign must preserve these distinctions.

## Priority and decision rules

**P1:** address first because the highest finding on the route affects task completion, trustworthy data interpretation, consequential actions, accessibility or a substantial workflow boundary. **P2:** improve efficiency, consistency and navigation after the P1 foundations. **P3:** retain the current structure, with limited polish or verification. No P0 production incident is established by this audit.

The route counts are **44 P1, 30 P2 and 7 P3**. These are not 81 separate redesign projects: shared recovery, controls, pagination and record patterns account for many affected routes. The delivery sequence below groups them into coherent work packages.

Evidence labels in this report:

- **Browser + source confirmed:** the controlled view reproduced a state and its implementation explains it.
- **Source confirmed:** a definite code path/control association is present or absent; it may still need an interactive reproduction for exact timing or role combinations.
- **Design recommendation:** a proposed task boundary or hierarchy based on the existing workflow, requiring design/implementation review.
- **Contract validation needed:** a proposal depends on API support, aggregation semantics or permission provenance that this frontend review does not establish.

## Highest-impact findings

### 1. Failures can look like successful empty results — P1

**Browser + source confirmed.** Appointments, asset loans, asset maintenance, department lists, cell-group lists, the inbox and the form picker in Submissions present ordinary zero/empty messages after the corresponding data reads fail. The giving overview keeps placeholders/skeletons because `!summary` is treated as loading even after failure. The attendance overview can mix zero counts and empty activity after failed summary/trend reads. Detail pages for branches, roles, users, events and sermons also often call any fetch failure “not found”, which misdiagnoses outages.

Keep existing controls and user scope visible. Use persistent, section-specific errors and retry, reserve empty messages for successful zero results, and distinguish denied/unavailable/missing states. A list error should not cause staff to believe the church has no records or create duplicate work. Do not turn a partial dashboard failure into one blank page if unaffected sections can remain useful.

### 2. Attendance collections need explicit boundaries — P1

**Source confirmed; structure is a design recommendation.** `/attendance/records` stacks reported headcounts above named records, with independent filters and exports. `/attendance/reports` combines aggregate summaries/lists, named totals and derived chart breakdowns. Check-in places the general-totals panel before the member/visitor recording task. Department/group/service details repeat the same competing surfaces.

Use separate Named check-ins and Reported headcounts views for record browsing/reporting. In an individual meeting's Attendance workspace, labelled total and named-attendee sections can remain together when users need to compare them. Keep the meeting/service/date context visible. Never sum headcounts and named check-ins into an invented larger attendance total. Each collection owns its filters, paging, export and mutations.

### 3. Assets promise operational worklists but show equipment lists — P1

**Browser + source confirmed.** `/assets/loans` lists Asset, Condition, Status and Current Value; borrower, due date and overdue state are absent. `useAssetLoans` runs only after opening an asset drawer. `/assets/maintenance` similarly lists equipment currently marked maintenance, not scheduled/in-progress/completed work. Users have to inspect assets one at a time to find operational obligations.

Give loan and maintenance records their own worklist structure. Keep the asset register as the equipment inventory. Asset creation/editing belongs on a spacious full page with Identity, Assignment/location and Valuation categories: the existing form has more than 20 inputs inside a 640px modal. Keep the quick detail drawer if helpful, but provide a stable record route for multiple histories, QR and depreciation.

**Contract validation needed:** current frontend hooks are asset-scoped for loans/maintenance. Confirm church-wide operational listing support, filtering and grants before promising all-loan/all-job tables; do not fabricate rows or change financial/depreciation rules as a UI cleanup.

### 4. Long record pages mix unrelated tasks — P1

**Source confirmed; design recommendation.** Member detail combines contact/membership with giving, attendance and notes. Department detail starts with two attendance panels before details and roster. Cell-group detail combines membership, two attendance modes, nearby groups and giving. Forms place questions/access administration before submissions review.

Keep essential record identity and action context visible. Separate substantial related tasks into permission-aware views, not nested cards. Keep small single-task records, such as family membership and a branch's contact/location, as well-structured single pages. Do not impose the same tabs on every record.

### 5. Form authoring exposes implementation details and false affordances — P1

**Browser + source confirmed.** Every question is expanded with internal Field Key, type, Required and options. A drag-grip icon is rendered without reordering handlers. Labels in FormFieldsEditor and FormSettingsCard are frequently plain Label siblings without `htmlFor`/IDs or another accessible association; the required/public/template switches need explicit names. Four simple questions already produce a long editor before collection settings begin.

Use a question outline plus a focused editor and preview. Keep stable keys accessible under advanced editing without renaming existing answer identifiers. Provide actual keyboard reorder actions if reordering is supported; otherwise remove the misleading grip. Associate every control and helper/error with its label. Keep question writing separate from publication, sharing and duplicate-response protection. Question updates already set React Hook Form dirty state; preserve that working behaviour.

### 6. Some visible controls cannot complete the action they suggest — P1

**Source confirmed.** Appointments passes `page`, fixed `perPage={15}` and no `onPerPageChange` to TableCard. CellGroupGivingPanel does the same. TableCard substitutes a no-op handler, while TablePagination still offers Rows per page. Selecting another size cannot change the displayed page size. The form question grip also suggests a missing reorder action.

Wire real page-size state/API limits, or render a fixed-size pager without the selector. Do not remove working pagination. Add focused tests with enough rows for the control to be visible. Retain the setting's value when moving between related views.

### 7. Shared table configuration contributes to clutter everywhere — P2 foundation

**Source confirmed and visible in populated examples.** Table unconditionally renders Table view, Column actions and Columns controls, even for small setup tables. Export/selection add further buttons and checkboxes. Density/visibility functions are useful, but repeated control rows can dominate a three-column directory or every nested table.

Expose one secondary Table options menu with labelled Density and Columns groups. Keep data Export in the collection header and selected-record actions in a selection bar. Preserve column visibility, widths, density, pinned identifiers, keyboard scrolling and selected export. Keep configuration discoverable without requiring it to occupy a full row on every table. Do not remove a table's comparison function by replacing it with cards.

### 8. Tablet layout uses viewport breakpoints despite a narrow content area — P1 where reproduced

**Browser + source confirmed.** At 768px, the open sidebar leaves about 512px before main padding. `/assets` produced document width **775px** and `/events/registrations` **823px**. Their fixed-width filter groups exceed the remaining area. Phone layouts may pass because they have already switched to vertical stacking; desktop-only and phone-only checks miss this.

Use wrapping/grid rules based on available main-content width, with `min-w-0` and sensible control minimums; consider component/container breakpoints for dense toolbars. Keep wide data tables inside their own scroll regions. Fix page-level overflow without shrinking text or clipping critical controls. Recheck with sidebar expanded/collapsed and long names/options, not just empty screens.

### 9. Local state and programmatic navigation leave draft/history gaps — P1/P2 by workflow

**Source confirmed; exact loss timing needs interaction regression.** The shared guard intercepts anchors and unload, but Back/Cancel buttons call router.push/back directly on several long forms. Settings/user tabs are local, and inactive Radix content normally unmounts. Other drafts live in plain component state: imports, media queues, form responses, provider credentials and permission selection. Some editors also reset values whenever fetched records change.

Route all explicit exit actions through a draft-aware path or preserve the editing session. Keep drafts during related-view switches and make errors discoverable without clearing input. Use URL state for shareable task context; preserve unrelated query parameters. Do not blindly add URL tabs to a workflow whose inactive content loses drafts. Do not retain/re-display provider secrets contrary to their existing write-only contract.

### 10. Sampled data is presented like complete summaries — P1

**Source confirmed.** Families derives With head/linked-member metrics from at most **100 families**. Visitor Follow-Up loads **200 visitors** into a local board. Broadcast summaries inspect at most **100 broadcasts**. Attendance Reports derives By Service from a **200-record window**. The calendar initially loads **100 events/services** rather than a proven complete visible date range.

Use authoritative aggregate endpoints or fully paginated results where appropriate. If a view remains partial, state exactly what it covers and provide a way to reach the rest. A small summary must not imply completeness that the query cannot establish. Do not change plan/branch/ownership rules to make the aggregate convenient.

### 11. Consequential actions need scope and consequence before the click — P1

**Source confirmed; no action was executed in this audit.** Inbox Delete forever calls the mutation directly. Form Regenerate immediately replaces the public link and only explains afterwards that the old URL no longer works. Provider Archive account can block service bindings, with dependency consequences explained mainly in surrounding prose.

Use focused confirmations naming the message/form/account and the real consequence; show dependent services before archiving an account. Keep ordinary reversible trash actions lightweight. Preserve failure context and focus return to the originating control. Keep broadcasts' already-working Send Broadcast versus Schedule Broadcast wording; add a review summary of content/audience/time rather than claiming the current button fails to distinguish them.

### 12. Reporting context, duplicate charts and navigation overlap — P1/P2

**Source confirmed; some contract validation needed.** Giving Analytics renders the same category data as both a bar chart and BreakdownBars. Member/Attendance Analytics have no visible date/branch controls even though the hooks accept range parameters. Giving Analytics uses fixed naira formatting while Giving Reports chooses a currency from transaction rows. A report-data error replaces the report generator's setup, preventing users from changing the specification that failed. Overall Giving Report export is nested in a By Category chart header.

Keep module overviews for operations, analytics for interpretation and `/reports` for export composition; clarify labels and context instead of blindly merging routes with different plan/grant requirements. Use one category representation plus optional exact values. Put report-wide export at report level and preserve the report specification on failures. Confirm server currency/aggregation semantics before alleging mixed-currency totals or changing financial calculations.

### 13. Administrative ownership and permission semantics need clearer surfaces — P1

**Source confirmed; design/contract follow-up.** Settings mixes tenant General settings, personal Security and the complete Integrations editor; Integrations is also independently routed. A role matrix permits unchecking many inherited default grants even though the API retains them, explaining the discrepancy after Save. Role grants and HQ/branch data scope are independently meaningful and must not be conflated.

Make Profile the canonical personal-security destination and select one canonical integrations route with compatible existing links. Keep role discovery separate from grant editing. Show inherited versus church-added grants before editing, with disabled states/explanations that match actual revocability. Preserve custom-role direct-edit semantics, protected administrator grants, reset confirmation and plan restrictions. If provenance is missing from the role response, confirm how it can be derived/exposed before presenting a definitive inherited/override breakdown.

### 14. Semantic headings and explicit reading/navigation actions are inconsistent — P1/P2

**Source confirmed, with populated checks on forms/user detail.** Several successful record pages use h2 or CardTitle divs as the page name without a page h1. Form Fill has a generic PageHeader h1 plus a second form-title h1. CardTitle defaults to a div, so many section labels are visual rather than semantic headings. Many rows depend on cell/row click; pastoral read-only users see clamped note text without an explicit complete-note View action. Active/Archived uses plain buttons without selected-state semantics. Breadcrumbs often repeat the shared Dashboard/Home entry.

Provide one meaningful h1 per page, labelled h2/h3 sections, explicit record links or View controls, and named/selected-state semantics for controls. Keep the shared skip link, focus styles, Radix focus trapping and scrollable table regions. Provide complete authorised note content to readers without requiring edit permission. Consolidating administrative actions should not remove their keyboard access.

## Concrete structure for the most overloaded remaining page

`/departments/cell-groups/[groupId]` needs the strongest structural intervention.

| Region | Content and action scope |
| --- | --- |
| Persistent record header | Group name as h1, branch, leader, meeting day/time, compact location summary and archived state. Group-level Edit/Archive/Delete/Restore live in one secondary actions menu with their existing grants. |
| Members workspace | Roster and member count; Add Member beside the roster; remove membership per row with the existing own-group restrictions. Do not place financial or attendance filters here. |
| Attendance workspace | Shared selected meeting/date context. Clearly labelled Reported totals and Named attendees sections, with their own Record total and Mark attendance actions. Keep exports/counts scoped. Do not add the two measures. Keep a filter visible beside the collection it affects if the existing APIs cannot share date scope. |
| Giving workspace | Combined meeting giving, category, method, date and receipts; Record Meeting Giving beside this collection. Fix the ineffective page-size selector. Do not introduce individual giver fields into the group-total workflow. |
| Secondary group context | Full address, map/coordinates and Nearby groups in a labelled location section/disclosure. Nearby discovery should not take a permanent third column away from meeting operations. |
| Permission-aware default | A viewer allowed only financial group data lands in Giving and never starts member/attendance queries. Group leaders retain ownership checks. Read-only staff see the same task organisation without write actions. |
| View and draft state | Meaningful URL state such as `?tab=attendance&date=...`, with valid fallback for an unavailable tab, unrelated query preservation, predictable Back/Forward and retained in-progress attendance/giving drafts. |

The existing group route remains the record boundary; no mandatory new child routes are needed for these related tasks. Asset loan and maintenance worklists, in contrast, need their own true record collections because their purpose spans many assets. That difference is deliberate.
